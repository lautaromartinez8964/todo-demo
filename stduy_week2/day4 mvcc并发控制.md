## 第一章：先比喻后理论 —— 什么是 MVCC？

### 1.1 遥感直觉类比：多时相卫星影像（Multi-temporal Imagery）

在遥感中，如果你想分析 2020 年到 2026 年某地区的城市扩张：
*   你**不需要**去把 2026 年地表上的房子拆了去还原 2020 年的样子。
*   你只需要去影像库里调用 **2020 年的历史卫星遥感快照（Snapshot）**。

在数据库中：
*   如果写操作（`UPDATE`）需要修改一行数据，而读操作（`SELECT`）此时也要看这行数据。
*   最简单粗暴的方法是**加锁排队**：写的时候不准读，读的时候不准写。但这会导致高并发性能急剧下降。
*   **MVCC（Multi-Version Concurrency Control，多版本并发控制）** 就是数据库的“历史影像库”。它允许**“无锁并发读写”**——写操作去修改最新的数据，读操作去读历史版本的快照，**互不阻塞，性能极大提升** [2]！

---

### 1.2 概念区分：快照读 vs 当前读

在学习 MVCC 之前，必须分清 MySQL 里的两种读取行为：

1.  **快照读（Snapshot Read）**：
    *   普通的 `SELECT` 语句（不加锁）。
    *   **特点**：利用 MVCC 读取数据的历史快照版本，**不需要加锁** [2]。
    *   *例如*：`SELECT * FROM account WHERE id = 1;`
2.  **当前读（Current Read）**：
    *   特殊的读取操作，或者是 `UPDATE`、`DELETE`、`INSERT` 写操作。
    *   **特点**：读取的是数据的**最新提交版本**，并且读取时**必须对数据加锁**。
    *   *例如*：
        *   `SELECT * FROM account WHERE id = 1 FOR UPDATE;` （加排他锁）
        *   `SELECT * FROM account WHERE id = 1 LOCK IN SHARE MODE;` （加共享锁）
        *   `UPDATE account SET balance = 500 WHERE id = 1;` （当前读）

## 第二章：MVCC 的三大物理基石

MVCC 不是凭空运行的，它依赖 InnoDB 引擎内部的 **三大物理结构**：

### 基石 1：隐藏列（`DB_TRX_ID` 与 `DB_ROLL_PTR`）

在 Day 3 中我们提到，聚簇索引叶子节点上的每一行数据，都有两个隐式字段：
*   **`DB_TRX_ID`**：记录最后一次修改该行记录的**事务 ID**（自增递增的数字）。
*   **`DB_ROLL_PTR`**：指向 `undo log` 中上一个历史版本的指针。

---

### 基石 2：`undo log` 版本链（Version Chain）

每当有事务对某行数据进行 `UPDATE` 或 `DELETE` 时，InnoDB 会将旧版本写入 `undo log`，并通过 `DB_ROLL_PTR` 将这些旧版本按**从新到旧**的顺序单向串联起来 [2]。

#### 物理版本链示例图：
假设表里有一条初始数据 `balance = 1000`（由事务 50 创建）：

```text
+-------------------------------------------------------------------------------+
| 聚簇索引数据页 (最新记录)                                                      |
| id=1 | balance=500 | DB_TRX_ID=102 | DB_ROLL_PTR ────────────────────+         |
+---------------------------------------------------------------------│---------+
                                                                      │
                                                                      ▼
+-------------------------------------------------------------------------------+
| undo log 回滚段 (旧版本链)                                                   |
| id=1 | balance=800 | DB_TRX_ID=101 | DB_ROLL_PTR ───+                            |
+--------------------------------------------------│----------------------------+
                                                   │
                                                   ▼
+-------------------------------------------------------------------------------+
| id=1 | balance=1000 | DB_TRX_ID=50 | DB_ROLL_PTR = NULL                       |
+-------------------------------------------------------------------------------+
```

这个由隐藏指针串联起来的历史版本集合，就是 **`undo log` 版本链** [2]。

---

### 基石 3：`ReadView`（读视图 / 快照权限卡）

当你的事务执行 `SELECT` 语句（快照读）时，InnoDB 会在内存中为你生成一个数据结构，叫做 **`ReadView`** [2]。

**`ReadView` 相当于给当前事务发了一张“快照权限卡”，决定了当前事务“有权看到版本链上的哪一段数据”。**

---

## 第三章： ReadView 4 大核心字段与可见性算法

这是 MVCC 中最核心的数学推导部分，请跟着步骤推导。

### 3.1 `ReadView` 结构里的 4 个核心字段

在生成 `ReadView` 的那一个瞬间，MySQL 会拍摄一张当前活跃事务的“快照”，记录 4 个变量：

```text
                 ReadView 结构体内部
+---------------------------------------------------+
| m_ids        : [100, 101]   (当前活跃/未提交事务列表)|
| min_trx_id   : 100          (m_ids 中最小的事务 ID) |
| max_trx_id   : 102          (系统即将分配的下一个 ID)|
| creator_trx_id: 102         (创建本 ReadView 的事务 ID)|
+---------------------------------------------------+
```

1.  **`m_ids`**：在生成 ReadView 时，系统里**正在运行且尚未提交（Uncommitted）**的事务 ID 数组。
2.  **`min_trx_id`**：`m_ids` 列表中最小的那个事务 ID。
3.  **`max_trx_id`**：系统即将分配给下一个新事务的 ID（**注意：不是 `m_ids` 中的最大值，而是全局最大事务 ID + 1**）。
4.  **`creator_trx_id`**：生成这个 ReadView 的当前事务自己的 ID。

---

### 3.2 判定规则：版本可见性匹配算法（规则匹配表）

当事务 X 带着自己的 `ReadView` 去沿着 `undo log` 版本链从头往尾找数据时，每遇到一个版本的记录（假设该记录的 `DB_TRX_ID` 为 `trx_id`），按照以下 **4 步规则依次比对**：

```text
                            [ 检查版本的 DB_TRX_ID ]
                                       │
         ┌─────────────────────────────┼─────────────────────────────┐
         ▼                             ▼                             ▼
【规则 1】trx_id == creator_trx_id    【规则 2】trx_id < min_trx_id     【规则 3】trx_id >= max_trx_id
  └─► 是自己修改的                   └─► 读视图创建前已提交            └─► 读视图创建后才开启
  └─► ✅ 物理可见                    └─► ✅ 物理可见                   └─► ❌ 物理不可见
                                       │
                                       ▼ (如果在 min 和 max 之间)
                                 【规则 4】min_trx_id <= trx_id < max_trx_id
                                       │
                       ┌───────────────┴───────────────┐
                       ▼                               ▼
               trx_id 在 m_ids 中              trx_id 不在 m_ids 中
             └─► 事务尚未提交                └─► 事务已经提交
             └─► ❌ 物理不可见                 └─► ✅ 物理可见
```

#### 算法文字法则（必须记牢）：
1.  **如果 `trx_id == creator_trx_id`**：说明这个版本就是我自己修改的！➔ **✅ 可见**。
2.  **如果 `trx_id < min_trx_id`**：说明修改这个版本的事务，在我的 ReadView 生成之前就已经提交了！➔ **✅ 可见**。
3.  **进入规则 3 前：如果 `trx_id >= max_trx_id`**：说明修改这个版本的事务，是在我的 ReadView 生成之后才开启的！➔ **❌ 不可见**（不能看未来的数据）。
4.  **如果 `min_trx_id <= trx_id < max_trx_id`**：
    *   检查 `trx_id` 是否在 **`m_ids` 列表** 中：
        *   **如果在 `m_ids` 中**：说明生成 ReadView 时，这个事务还在运行、还没提交！➔ **❌ 不可见**。
        *   **如果不在 `m_ids` 中**：说明生成 ReadView 时，这个事务已经提交了！➔ **✅ 可见**。

> 📌 **丢弃逻辑**：一旦判定某个版本 **不可见**，MySQL 就会沿着 `DB_ROLL_PTR` 指针去找 `undo log` 里的**上一个更老版本**，重复套用上面的 4 步规则比对，直到找到第一个 **✅ 可见** 的版本为止！

## 第四章：终极解密 —— RC 与 RR 在 MVCC 实现上的本质差异

既然 RC（读已提交）和 RR（可重复读）都使用了 MVCC 机制，为什么 RC 会发生“不可重复读”，而 RR 不会 [2]？

**答案只有一句话：生成 ReadView 的物理时机不同！**

```text
RC (读已提交)  : 事务中【每一次 SELECT】都会重新生成一份新的 ReadView！
RR (可重复读)  : 事务中【仅在第一次 SELECT】时生成 ReadView，后续整个事务全程复用它！
```

---

### 物理推导对比：

假设事务 100 修改了数据并提交，事务 200 执行了两次 `SELECT`：

*   **在 RC（读已提交）级别下**：
    *   第一次 `SELECT` ➔ 生成 ReadView 1 ➔ 事务 100 还没提交，`100` 在 `m_ids` 里 ➔ 读到旧值。
    *   事务 100 此时 `COMMIT;` 提交了。
    *   第二次 `SELECT` ➔ **销毁旧 ReadView，重新生成 ReadView 2** ➔ 此时事务 100 已经提交了，`100` **不在**新的 `m_ids` 里 ➔ **读到了事务 100 修改的新值（不可重复读发生！）** [2]。

*   **在 RR（可重复读）级别下**：
    *   第一次 `SELECT` ➔ 生成 ReadView 1 ➔ 事务 100 还没提交，`100` 在 `m_ids` 里 ➔ 读到旧值 [2]。
    *   事务 100 此时 `COMMIT;` 提交了。
    *   第二次 `SELECT` ➔ **不生成新 ReadView，继续使用第一次的 ReadView 1**！ ➔ 在 ReadView 1 的视角里，`100` 依然在 `m_ids` 里 ➔ **依然读到旧值（消灭了不可重复读！）** [2]。

此时，这行数据的 **`undo log` 版本链** 从最新到最老如下：
*   版本 3（最新）：`name = 'B'`, `DB_TRX_ID = 101`

*   版本 1（最老）：`name = 'Original'`, `DB_TRX_ID = 50`

此时事务 102 生成的 **`ReadView` 字段如下**：
*   `creator_trx_id` = 102
*   `m_ids` = `[100, 101]`（事务 100 和 101 都未提交）
*   `min_trx_id` = 100
*   `max_trx_id` = 103（当前最大 102 + 1）

---

### 事务 102 的算法匹配推演过程：

1.  **检查 版本 3（`name = 'B'`, `trx_id = 101`）**：
    *   `trx_id = 101`。处于 `min_trx_id` (100) 和 `max_trx_id` (103) 之间。
    *   检查 `m_ids` 列表：`101` 在 `m_ids` 数组中！
    *   根据规则 4 判定：**❌ 不可见！**
    *   沿指针追溯到下一个版本（版本 2）。

2.  **检查 版本 2（`name = 'A'`, `trx_id = 100`）**：
    *   `trx_id = 100`。处于 `min_trx_id` (100) 和 `max_trx_id` (103) 之间。
    *   检查 `m_ids` 列表：`100` 在 `m_ids` 数组中！
    *   根据规则 4 判定：**❌ 不可见！**
    *   沿指针追溯到下一个版本（版本 1）。

3.  **检查 版本 1（`name = 'Original'`, `trx_id = 50`）**：
    *   `trx_id = 50`。
    *   比较 `min_trx_id`：$50 < 100$（`trx_id < min_trx_id`）。
    *   根据规则 2 判定：**✅ 可见！**

4.  **最终输出结果**：事务 102 成功读到了 `name = 'Original'`。算法推演完美闭环！

### 1. 事务 400 的 ReadView 4 个字段
*   **`m_ids` = `[200]`** （生成 ReadView 时，事务 300 已提交，唯独事务 200 尚未提交）。
*   **`min_trx_id` = `200`** （`m_ids` 中的最小 ID）。
*   **`max_trx_id` = `401`** （系统即将分配给下一个新事务的 ID）。
*   **`creator_trx_id` = `400`** （创建本 ReadView 的事务 ID 本身）。

### 2. 版本 C (`balance = 3000`, `trx_id = 300`) 的可见性推演
*   **推演规则**：`trx_id = 300` 介于 `min_trx_id` (200) 与 `max_trx_id` (401) 之间（满足规则 4：$200 \le 300 < 401$）。
*   **判定结论**：检索 `m_ids` 列表，`300` **不在 `m_ids` 数组中**。这物理证明了修改该版本的事务 300 在 ReadView 生成前已经提交，因此该版本 **✅ 物理可见**。

### 3. 事务 400 最终读取结果
*   最终返回 **`3000`**。

### 4. RC 与 RR 隔离级别的 MVCC 物理本质区别
> **满分标准表达**：
> 1. **RC (读已提交)**：事务中**每一次执行 `SELECT` 语句都会重新生成一份全新的 ReadView** [2]。若其他事务在两次 `SELECT` 之间提交了修改，新 ReadView 的 `m_ids` 中将不再包含该事务，导致新修改的数据变得可见，产生不可重复读 [2]。
> 2. **RR (可重复读)**：事务中**仅在第一次执行 `SELECT` 语句时生成 ReadView**，随后整个事务生命周期内一直**复用**该 ReadView [2]。即使其他事务中途提交了修改，由于复用的 ReadView 中的 `m_ids` 快照未变，依然判定该修改不可见，从而在物理上消灭了不可重复读 [2]。
