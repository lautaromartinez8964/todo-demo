### 👿 杀手题（面试官追问与满分回答）
*   **面试官追问**：“如果一个 Goroutine 写了死循环 `for {}`，会卡死对应的 P 甚至整个进程吗？Go 是如何解决的？”

### 👿 杀手题（面试官追问与满分回答）
*   **面试官追问**：“向一个已满的 Channel 发送数据，底层具体发生了什么？会一直持有锁吗？”
*   **满分回答**：不会一直持有锁。1. 协程首先获取 `hchan.lock` 互斥锁。2. 检查缓冲区，发现已满且无等待接收者。3. 在堆上分配一个 `sudog` 结构，打包当前的 Goroutine。4. **将当前 G 放入 `sendq` 等待队列，然后释放 `hchan.lock` 锁**。5. 调用 `gopark` 让出 CPU 权限，G 进入 waiting 状态，等待被唤醒（在此期间锁已被释放，其他协程可以读该 channel）。当有接收者时，接收者直接从 `sudog` 复制数据，并调用 `goready` 唤醒发送协程。

通过以下代码验证 defer 的参数即时计算（Pass-by-value）与 panic/recover 的拦截。

```go
package main

import "fmt"

func deferTiming() (result int) {
	defer func() {
		result++ // 这里修改了有名返回值变量 result
	}()
	return 1 // 第一步：result = 1; 第二步：执行 defer; 第三步：返回 result 
}

func deferParamEval() {
	a := 1
	defer func(x int) {
		fmt.Println("defer closure parameter:", x) // 输出 1，因为注册时参数已被计算并压栈
	}(a)
	a = 2
	defer fmt.Println("defer direct print:", a) // 输出 2，因为直接调用的参数注册时即求值，此时 a 已变为 2
}

func main() {
	fmt.Println("defer timing return value:", deferTiming()) // 应输出 2
	deferParamEval()
}
```

### 👿 杀手题（面试官追问与满分回答）
*   **面试官追问**：“Go 的 GC 是并发进行的，如果标记过程中用户协程（Mutator）修改了指针指向，导致黑色对象指向了白色对象，且灰色对象断开了对该白色对象的引用，会发生什么？Go 是如何解决的？”
*   **满分回答**：这会导致**垃圾误清理（悬空指针）**。Go 引入**混合写屏障**解决此问题，核心逻辑是：1. 任何在栈上创建的新对象均置为黑色。2. 被删除引用的对象标记为灰色（保护下游）。3. 被添加引用的对象也标记为灰色。通过这套机制确保了强/弱三色不变性，避免了未扫描的活跃对象被误杀，并且消除了栈上重新扫描（Rescan）所需的 STW。

### 👿 杀手题（面试官追问与满分回答）
*   **面试官追问**：“如果一个 goroutine 已经持有了 sync.Mutex，它在饥饿模式下释放锁，新来的 goroutine 能通过自旋（Spinning）抢占到这把锁吗？为什么？”
*   **满分回答**：不能。在饥饿模式下，锁的所有权会**直接传递**给等待队列头部的 goroutine。新来的 goroutine 即使在自旋，也绝对不会尝试去抢占锁（它们也不会进入自旋状态，而是直接被送入等待队列的尾部）。这样彻底杜绝了新协程通过 CPU 自旋把老协程“饿死”的情况。

### 🧪 验证实验
编写一个并发竞争 map 导致崩溃的代码，并利用 Go 编译器内置的 `-race` 工具进行死锁/竞争检测。

```go
package main

import (
	"sync"
	"time"
)

func main() {
	m := make(map[string]int)
	var lock sync.Mutex

	// 并发写同一个 map
	for i := 0; i < 10; i++ {
		go func() {
			lock.Lock()
			m["key"] = 1
			lock.Unlock()
		}()
	}

	// 故意不加锁去读，制造 race 冲突
	go func() {
		_ = m["key"] 
	}()

	time.Sleep(100 * time.Millisecond)
}
```
**运行验证命令**：
```bash
go run -race race.go
```
观察检测工具是如何清晰地打印出哪两行代码在进行非安全的读写竞争（Write/Read Data Race）。

### 📝 20 题终极自测清单

#### 1. GMP 模型中，P（Processor）的作用是什么？为什么不直接用 M（Machine）去调度 G（Goroutine）？
*   **满分要点**：
    *   引入 P 的核心目的是为了降低多线程对全局队列的**锁竞争**，每个 P 拥有自己的本地队列（Local Runqueue） [1]。
    *   若无 P，当 M 发生系统调用（Syscall）阻塞时，其持有的所有 G 将无法执行，而有了 P 之后，M 阻塞时，P 会与 M 解绑（Hand Off 机制），被分配给新的 M 继续执行，提升系统的并发吞吐率。

#### 2. 协程从创建到执行，会经历哪些队列？请画出其生命周期的完整流转路线。
*   **满分要点**：
    *   新创建的 G 优先放入当前 P 的 `runnext`（插队机制，高优先级） [1]。
    *   若 `runnext` 满了，放入 P 的本地队列（Local Runqueue，容量 256） [1]。
    *   若本地队列也满了，会将本地队列的前一半连同新 G 一起放入全局队列（Global Runqueue，加锁） [1]。
    *   当 M 调度时，获取 G 的顺序是：`runnext` -> 本地队列 -> 全局队列 -> Work Stealing 窃取其他 P 队列尾部的 G [1]。

#### 3. 什么是工作窃取（Work Stealing）？它在 GMP 中具体是如何执行的？其算法耗时和锁竞争情况如何？
*   **满分要点**：
    *   当某 M 绑定的 P 本地运行队列及全局队列均无 G 时，会尝试从其他 P 的本地运行队列中**窃取（Steal）**一半的协程过来执行 [1]。
    *   窃取是从其他 P 本地队列的**尾部**（Tail）以无锁的形式获取（因为本地 P 消费是从头部 Pop，窃取从尾部 Steal，通过原子操作（CAS）避免锁竞争，性能极高） [1]。

#### 4. 为什么 Go 的协程比操作系统的线程轻量？请从内存和切换成本量化分析。
*   **满分要点**：
    *   **内存占用**：操作系统线程栈是固定大小（通常是 2MB~8MB），而 Go 协程的栈采用动态收缩和扩容（栈分裂），初始化只有 **2KB** 左右。
    *   **切换成本**：线程切换涉及特权级转换（内核态与用户态转换），需要保存/恢复寄存器（FPU、MMX、SSE 等浮点计算上下文），大约需 1000~2000 周期。而协程切换在用户态完成，只需保存少数通用寄存器（SP、BP、PC 等），耗时极短，大约需十几到几十周期。

#### 5. 在 Go 运行时中，Sysmon 监控线程扮演了什么角色？
*   **满分要点**：
    *   Sysmon 是一个不需要绑定 P、直接在系统线程（M）上运行的后台守护协程（每 10ms 或更短时间唤醒一次）。
    *   其职责包括：1. 释放闲置超过 5 分钟的物理内存（Madvising）；2. 触发强制垃圾回收（如果超过 2 分钟未发生 GC）；3. 抢占长时间运行的 G（运行时间 > 10ms 会被标记抢占信号）；4. 剥离由于系统调用（Syscall）阻塞的 M 上的 P（Hand Off）。

#### 6. 为什么在 Go 中局部变量返回其指针，不一定会逃逸？请结合编译器行为分析。
*   **满分要点**：
    *   局部变量是否分配在堆上是由**逃逸分析（Escape Analysis）**在编译期决定的。
    *   如果局部变量返回指针，但编译器发现该指针在外界并没有任何“生命周期逃出当前函数作用域”的引用，或者通过内联（Inlining）优化直接在调用方内部分配，它依然可以安全地分配在栈上，避免堆分配的开销。

#### 7. 请说出 3 种在编写业务代码时，一定会导致变量逃逸到堆上的高频场景。
*   **满分要点**：
    *   1. 指针逃逸：函数返回局部变量的指针，且该指针在外部有引用。
    *   2. 动态类型逃逸：调用接收空接口 `interface{}` 的函数，如 `fmt.Println(any)`，因为反射需要变量地址。
    *   3. 闭包逃逸：闭包内部引用了其外部函数的局部变量。
    *   4. 空间过大逃逸：申请的 slice 或 map 尺寸太大（例如超过 64KB）或者容量无法在编译期确定。

#### 8. Channel 的底层是如何保证线程安全的？
*   **满分要点**：
    *   Channel 的底层 `hchan` 结构体中包含了一个互斥锁 `lock mutex`。
    *   对缓冲区的读写操作、对发送接收队列（`sendq`/`recvq`）的入队出队操作，都在加锁状态下完成。因为在锁的保护下，同一时间只有一个 Goroutine 能修改 `hchan` 的状态，所以它是并发安全的。

#### 9. 非缓冲 Channel（Unbuffered）和缓冲 Channel（Buffered）在底层发送与接收的逻辑有什么本质差异？
*   **满分要点**：
    *   **非缓冲 Channel**：发送和接收必须**同步相遇**。发送时如果无接收者，G 立即入队 `sendq` 并挂起；如果已有接收者在 `recvq` 等待，发送者直接将数据拷贝到接收者的内存空间（不经过环形缓冲区），调用 `goready` 唤醒接收者（减少一次内存拷贝）。
    *   **缓冲 Channel**：发送者在缓冲区未满时，直接将数据写入环形数组 `buf` 对应的插槽，移动 `sendx` 索引，发送者不阻塞。只有当缓冲区满时，发送者才会被挂起放入 `sendq`。

#### 10. 尝试向一个已经关闭（Closed）的 Channel 写入和读取数据，底层分别会发生什么？
*   **满分要点**：
    *   **向已关闭的 Channel 写入**：会直接触发 **Panic**。
    *   **从已关闭的 Channel 读取**：如果环形缓冲区内仍有剩余数据，会正常读取数据；如果数据已经读完，会**立即返回通道元素类型的零值**，且多变量接收时的第二个参数 `ok` 变为 `false`。

#### 11. 什么是协程泄漏（Goroutine Leak）？如何利用 Channel 故意制造一个泄漏？又如何用 context 修复？
*   **满分要点**：
    *   **协程泄漏**是指由于逻辑Bug，某些 Goroutine 永远处于阻塞（等待接收或发送）状态，且没有被外部主动结束，导致其所占的栈内存和 runtime 数据结构永远无法被 GC 释放。
    *   **制造泄漏**：让一个 G 尝试读取一个永远没有协程向其写入的非缓冲 Channel。
    *   **使用 context 修复**：在 G 内部使用 `select` 监听 `ctx.Done()`，在外部主协程需要结束时，调用 `cancel()` 关闭 Context。G 收到信号后退出函数。

```go
select {
case <-ch: // 正常业务
case <-ctx.Done(): // 收到取消信号，安全退出，防止泄漏
    return 
}
```

#### 12. Go 的 Defer 是在什么时候求值的？请解释传值（Value）和传闭包（Closure）的差异。
*   **满分要点**：
    *   `defer` 后跟着的函数的参数，是在 **`defer` 语句被注册的瞬间立即计算求值的**（传值拷贝，即使后续变量发生修改，defer 执行时也是用当时计算的值）。
    *   但如果 defer 引用的是一个闭包（Closure），且该闭包直接捕获了外部的变量（未通过参数传递），那么当 defer 真正执行（即函数 return 前夕）时，它会去读当前这个被捕获变量的最新值。

#### 13. 如果在多个 Defer 函数中修改同一个命名返回值，最终函数的返回值会是谁修改的结果？
*   **满分要点**：
    *   最终返回值是**最后一个执行的 defer（因为是 LIFO 栈顺序）修改后的结果**。
    *   命名返回值变量在函数一开始就被定义，在 `return xxx` 执行时，xxx 的值会被赋值给这个命名变量，接着按 LIFO 顺序执行 `defer` 链表。由于 defer 直接操作的就是这个命名返回值变量，所以其最终值由最后一个执行的 defer 决定。

#### 14. 为什么 recover() 必须直接写在 defer 定义的函数体内才有效？写在 defer 函数内部子函数里可以吗？
*   **满分要点**：
    *   因为在 panic 发生后，runtime 会遍历并调用协程上的 `_defer` 链表。在 `gopanic` 的循环中，recover 的有效性受到严格限制。
    *   `recover()` 底层会检查当前正在执行的 `_defer` 结构。它要求调用者必须是当前被 runtime 调起的那一个 defer 函数本体，无法跨调用栈捕获。如果写在 defer 函数内部的子函数中，或者通过其他间接层级调用，底层检查会失效，返回 `nil`。

#### 15. Go 的垃圾回收（GC）采用的三色标记法中，灰色对象（Grey）的作用是什么？为什么只用黑色和白色不行？
*   **满分要点**：
    *   灰色对象在逻辑上充当了**扫描进度中的“波面（Wavefront）”**。它代表当前对象是活跃的、已被追踪到，但它引用的下游子对象**还没有被扫描**。
    *   如果只有黑白两色：当 GC 标记活跃对象时，如果用户协程并发修改了指针，GC 无法区分一个已被扫描完的黑色对象和一个未被扫描的活跃对象，会导致遍历遍历中断，从而无法保证并发垃圾回收的准确性。

#### 16. Dijkstra 插入写屏障和 Yuasa 删除写屏障的核心区别是什么？Go 的混合写屏障吸收了它们什么优点？
*   **满分要点**：
    *   **Dijkstra 插入写屏障**：在黑色对象引用白色对象时，强制将白色标记为灰色（防止漏标）。缺点：栈上没有屏障，需要在标记结束时 STW 重新扫描栈，带来停顿。
    *   **Yuasa 删除写屏障**：在灰色或黑色对象删除对白色对象的引用时，强制将白色对象标记为灰色（保护下游）。缺点：垃圾回收精度低，且需要在 GC 开始时 STW 扫描并快照整个堆。
    *   **Go 混合写屏障**：结合了两者。**栈上不设屏障，新对象全置黑**（继承 Dijkstra 快速优点），同时**删除和新加引用的对象一律置灰**（继承 Yuasa 保护下游），从而彻底**消除了标记结束时重新扫描栈的 STW 开销**。

#### 17. sync.Mutex 的正常模式（Normal）和饥饿模式（Starving）是如何切换的？
*   **满分要点**：
    *   **正常切换到饥饿**：当一个 goroutine 尝试获取锁，在队列里等待的时间**超过 1ms** 时，它会将 Mutex 的状态变更为饥饿状态。
    *   **饥饿切换回正常**：在饥饿模式下释放锁时，如果：1. 当前拿到锁的 goroutine 是等待队列中的最后一个，或者 2. 它的等待时间小于 1ms，它就会将 Mutex 退回到正常状态。

#### 18. 在 sync.Mutex 饥饿模式下，刚到达的并发 Goroutine 为什么不再允许自旋（Spinning）？
*   **满分要点**：
    *   自旋（通过低成本的 CPU 循环指令等待锁释放）在锁释放瞬间，对 CPU 亲和性更高，几乎总能抢过刚从等待队列中被唤醒的协程（线程上下文切换慢）。这会导致等待队列中的老协程长期被抢占，“饿死”在队列中。
    *   在饥饿模式下，刚到达的协程不进行自旋，**直接排在等待队列尾部**，锁会严格按照 FIFO 顺序直接移交给队首老协程，保证调度公平性。

#### 19. sync.Once 底层如何利用双重检测锁（Double-Checked Locking）和原子操作保证 init 函数只执行一次且并发安全？
*   **满分要点**：
    *   `sync.Once` 内部有一个 `done uint32` 标记和一个 `m Mutex`。
    *   **第一次检测**：利用 `atomic.LoadUint32(&o.done) == 0`，如果为 1，直接快速返回（无锁，极快）。
    *   **加锁防并发**：若为 0，进入慢路径，获取互斥锁 `o.m.Lock()`。
    *   **第二次检测**：加锁后再次检查 `o.done`。如果不加锁检测，多个并发协程可能同时越过第一步检测，导致 init 执行多次。第二次检测后，执行函数，然后调用 `atomic.StoreUint32(&o.done, 1)`。

#### 20. sync.Pool 为什么能大大减轻 GC 压力？它的本地私有池（private）和共享池（shared）是如何协调性能的？
*   **满分要点**：
    *   `sync.Pool` 缓存了临时对象，实现了对象的**复用**，极大减少了由于高频创建临时对象导致的堆内存分配次数和 GC 回收开销。
    *   **存取协调**：
        1. 抢占锁优化：每个 P 都有自己的 `localPool`，分为一个 `private` 对象和一个 `shared` 双端队列。
        2. **读写无锁**：本 P 获取时先读 `private`（无锁，性能极佳）。
        3. 如果没有，读自己的 `shared` 头部（无锁 Pop）。
        4. 如果还没有，去别的 P 队列的 `shared` 尾部进行 **Work Stealing 窃取**（有锁，但低频）。
        5. 最后的防线：读 `victim`（受害者缓存，上轮 GC 遗存），若依然没有才调用 `New()` 创建。整个设计最大程度地消除了多线程之间的锁竞争。
