# 📋 Day 6 作业工业级标准答案

### 题目 1：写覆盖物理过程解析
> **满分标准表达**：
> 1. **内存与磁盘隔离**：`t.Likes++` 这一步仅发生在 Go 程序对应的 CPU 寄存器和 RAM 内存里，MySQL 磁盘/内存页中的数值尚未改变。
> 2. **更新丢失（Lost Update）**：当 Goroutine A 和 B 在各自独立的 Go 内存中同时读到初始值 `likes = 10` 并各自计算出 `11` 后，先执行 `db.Save()` 的 Goroutine A 将 MySQL 改为 `11`；随后执行 `db.Save()` 的 Goroutine B 再次将自己的内存值 `11` 发送给 MySQL，直接将 Goroutine A 的点赞结果**强行写覆盖**。最终两次点赞仅生效一次，产生更新丢失 Bug。

### 题目 2：悲观锁与乐观锁区别
> **满分标准表达**：
> 1. **悲观锁原生 SQL**：`tx.Clauses(clause.Locking{Strength: "UPDATE"}).First(&task)` 在物理上向 MySQL 发送了 **`SELECT * FROM tasks WHERE id = 1 FOR UPDATE;`** 带有排他锁的当前读语句 [2]。
> 2. **乐观锁 CAS 机制**：乐观锁通过应用层 CAS（Compare And Swap）机制 + `version` 版本列实现。当 SQL 返回 `RowsAffected == 0` 时，代表在读取与写入之间，**已有其他并发事务修改了该行记录并递增了 `version`**，导致当前 SQL 的 `WHERE version = V` 条件失效、未能匹配到任何行。
> 3. **选型**：在“写多读少”的高竞争并发场景下，乐观锁会导致大量 CAS 校验失败和重试，浪费 CPU 资源；此时更适用**悲观锁**。

### 题目 3：Git 变基命令
> **满分标准表达**：
> 1. **变基命令**：**`git rebase -i HEAD~4`**。
> 2. **编辑器操作**：将后 3 次提交开头的 `pick` 单词改成字母 **`s`**（即 `squash`，代表将其压缩合并入前一次提交）。

## 模块一：索引与 B+ 树物理结构（3 题）

### Q1：为什么 MySQL 选择 B+ 树而不是 B 树、Hash 表或红黑树？
> **标准答案**：
> 1. **对比 Hash**：Hash 表仅支持等值查询（$O(1)$），无法支持范围查询（如 `>`、`<`、`BETWEEN`）和排序。
> 2. **对比红黑树/AVL 树**：二叉树树高极高（$O(\log_2 N)$），千万级数据树高可达 20+，会导致 20+ 次磁盘 I/O。B+ 树通过多路高扇出（Fan-out），把树高压缩在 3~4 层，仅需 3 次磁盘 I/O。
> 3. **对比 B 树**：B 树非叶子节点存放整行数据，导致一页（16KB）存的指针变少、树变高。且 B 树叶子节点没有双向链表，做范围查询必须回溯遍历；而 B+ 树**非叶子节点只存索引列+指针**，叶子节点保存全量数据且通过**双向链表首尾相连**，范围扫描极快。

### Q2：什么是聚簇索引（Clustered Index）与二级索引（Secondary Index）？什么是回表？
> **标准答案**：
> 1. **聚簇索引**：以主键构建的 B+ 树，其叶子节点保存了整行记录的所有列字段 [2]。一张表有且仅有一个聚簇索引 [2]。
> 2. **二级索引**：以非主键列构建的 B+ 树，其叶子节点仅保存“索引列的值 + 主键 ID” [2]。
> 3. **回表**：当使用二级索引查询未覆盖的列时，MySQL 先在二级索引树查到主键 ID，再拿着主键 ID 去聚簇索引树重新检索整行数据的过程 [2]。

### Q3：如何消灭回表？（什么是覆盖索引？）
> **标准答案**：
> 当查询所需要的列（如 `SELECT id, scene_id`）全部包含在二级索引（如 `idx_scene`）的叶子节点中时，优化器跳过对聚簇索引的检索，直接在二级索引树上返回结果，这就是**覆盖索引（Covering Index）** [2]。`EXPLAIN` 的 `Extra` 列显式标注 **`Using index`** [2]。

## 模块二：EXPLAIN 执行计划与 Cost 成本模型（3 题）

### Q4：EXPLAIN 的 `type` 字段有哪些常见值？性能从好到坏怎么排序？
> **标准答案**：
> 排序：`const` > `eq_ref` > `ref` > `range` > `index` > `ALL` [2]。
> * `const`：主键/唯一索引等值查询，最多返回 1 行 [2]。
> * `ref`：普通二级索引等值查询 [2]。
> * `range`：索引范围扫描（`>`、`<`、`IN`、`BETWEEN`） [2]。
> * `index`：全索引扫描（扫描整棵二级索引树所有叶子）。
> * `ALL`：全表扫描（扫描整棵聚簇索引树所有叶子）。

### Q5：什么是复合索引的最左匹配原则？其物理原因是什么？
> **标准答案**：
> * **原则**：复合索引 `(a, b, c)` 在查询时必须从最左列 `a` 开始匹配，跳过 `a` 则无法使用索引；出现范围查询（如 `b > 10`）后，其右侧列（如 `c`）无法使用索引。
> * **物理原因**：在复合索引 B+ 树中，节点是按 `(a, b, c)` 字典序排列的。`a` 全局绝对有序；`b` 仅在 `a` 相等的局部有序；`c` 仅在 `a, b` 都相等的局部有序。若无最左列 `a`，整棵树的 `b` 是无序的，无法进行二分树查找。

### Q6：如何通过 `key_len` 计算推算出复合索引 `(a, b, c)` 中用上了几列？
> **标准答案**：
> 结合字符集和数据类型计算字节数（以 `utf8mb4` 为例）：
> * `INT NOT NULL` 为 4 字节；`BIGINT` 为 8 字节。
> * `VARCHAR(N)` 字节数 = $N \times 4 + 2 (\text{变长标识}) + 1 (\text{若允许 NULL})$。
> 对比 `EXPLAIN` 输出的 `key_len` 数值，若 `a` 算出来是 4 字节，`b` 算出来是 203 字节，实际 `key_len = 207` 时，代表 `a` 和 `b` 用上了索引，`c` 未用上。

## 模块三：事务 ACID 与日志体系（3 题）

### Q7：MySQL 是如何实现事务的原子性（A）和持久性（D）的？
> **标准答案**：
> 1. **原子性（A）**：由 **`undo log`（回滚日志）** 保障。记录修改数据的反向逻辑操作，回滚时按逆序执行反向 SQL 还原数据。
> 2. **持久性（D）**：由 **`redo log`（重做日志）** 和 **WAL 机制** 保障。事务提交时先顺序写磁盘 `redo log`，发生断电崩溃后重启读取 `redo log` 重新重做（Redo）脏页刷盘。

### Q8：什么是 WAL 机制？为什么写 `redo log` 比写数据页 `.ibd` 快？
> **标准答案**：
> * **WAL（Write-Ahead Logging）**：预写日志机制，修改内存脏页后不立刻刷数据页，而是先顺序写日志。
> * **优势**：写 `.ibd` 数据页属于**随机磁盘 I/O**（物理页分散在磁盘各处，寻道延时极高）；写 `redo log` 属于**顺序磁盘 I/O**（追加写入日志文件，寻道开销极小），速度快上千倍。

### Q9：什么是物理“页断裂（半写页）”？为什么需要双写缓冲区（Doublewrite Buffer）？
> **标准答案**：
> * **页断裂**：InnoDB 数据页为 16KB [5]，OS 磁盘块为 4KB。刷盘写入时若在中途（如第 8KB）断电，数据页损坏（半新半旧）。
> * **双写缓冲区救援**：`redo log` 物理重做依赖**数据页本身物理结构完整**，损坏页直接重做会导致错上加错。InnoDB 在刷盘前先将 16KB 页顺序复制到系统表空间的 Doublewrite Buffer 并刷盘；发生页断裂时，重启先从 Doublewrite Buffer 还原完整旧页副本，再应用 `redo log`。

## 模块四：MVCC 与 ReadView 可见性算法（3 题）

### Q10：什么是 MVCC？快照读与当前读有什么区别？
> **标准答案**：
> * **MVCC（多版本并发控制）**：通过维持数据的历史版本链，实现“无锁并发读写（快照读）” [2]。
> * **快照读**：普通 `SELECT`（不加锁），读取 MVCC 的 ReadView 历史快照 [2]。
> * **当前读**：`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`，读取最新提交的数据，并在物理索引节点上加排他锁。

### Q11：ReadView 的 4 个核心字段是什么？可见性匹配规则是什么？
> **标准答案**：
> 1. **4 个字段**：`m_ids`（当前活跃未提交事务 ID 列表）、`min_trx_id`（`m_ids` 最小值）、`max_trx_id`（系统下一个分配事务 ID）、`creator_trx_id`（当前事务 ID）。
> 2. **匹配规则**：
>    * `trx_id == creator_trx_id` ➔ ✅ 可见（自己修改）。
>    * `trx_id < min_trx_id` ➔ ✅ 可见（ReadView 生成前已提交）。
>    * `trx_id >= max_trx_id` ➔ ❌ 不可见（ReadView 生成后开启）。
>    * `min_trx_id <= trx_id < max_trx_id`：在 `m_ids` 列表中 ➔ ❌ 不可见（未提交）；不在 `m_ids` 列表中 ➔ ✅ 可见（已提交）。

### Q12：RC（读已提交）与 RR（可重复读）在 MVCC 实现上的物理本质区别是什么？
> **标准答案**：
> * **RC**：**每一次执行 `SELECT` 语句都会重新生成一份全新的 ReadView** [2]。
> * **RR**：**仅在事务中第一次执行 `SELECT` 语句时生成 ReadView**，随后整个事务生命周期内一直复用它 [2]。

## 模块五：锁体系与工程并发（3 题）

### Q13：InnoDB 锁的三种物理类型（Record/Gap/Next-Key Lock）分别是什么？
> **标准答案**：
> 1. **记录锁（Record Lock）**：锁住 B+ 树叶子节点上具体某一条物理行记录 [2]。
> 2. **间隙锁（Gap Lock）**：锁住两个索引记录之间的开区间 `(A, B)`，防止第三者 `INSERT`，防御当前读幻读。
> 3. **临键锁（Next-Key Lock）**：记录锁 + 间隙锁，锁住左开右闭区间 `(A, B]`，InnoDB RR 默认加锁单位。

### Q14：在 RR 隔离级别下，给主键做等值查询时，加锁降级规则是什么？
> **标准答案**：
> 1. **记录存在**：Next-Key Lock `(A, B]` 降级为 **记录锁 `[B]`** [2]。
> 2. **记录不存在**： Next-Key Lock `(A, B]` 退化为 **间隙锁 `(A, B)`** [2]。

### Q15：Go 后端写并发时，悲观锁与乐观锁（CAS）的本质区别是什么？
> **标准答案**：
> 1. **悲观锁**：依靠数据库底层排他锁（`SELECT ... FOR UPDATE`），读时即加锁，其他事务阻塞等待，强一致性，适用于高写竞争场景（如秒杀）。
> 2. **乐观锁**：依靠应用层 CAS 机制 + `version` 列（`UPDATE ... WHERE version = V`），读不加锁，写时比对版本；若 `RowsAffected == 0` 代表版本已被他人修改，进入重试，适用于高读低写场景。
