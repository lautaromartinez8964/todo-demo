# 📚 Day 1 深度精讲：MySQL InnoDB 存储物理引擎与 B+ 树

---

## 一、 为什么必须是 B+ 树？（从磁盘物理特性推导）

要理解 B+ 树，必须先理解**机械硬盘（HDD）与固态硬盘（SSD）的物理局限**。

### 1. 磁盘 I/O 是最大的性能瓶颈
*   **内存读写**：纳秒级（ns），速度极快。
*   **磁盘读写**：毫秒级（ms），比内存慢 10 万倍以上。磁盘读写涉及磁头寻道、盘片旋转（机械硬盘）或闪存块擦写（SSD）。
*   **结论**：**数据库性能优化的核心目标，就是极力减少“访问磁盘的次数（磁盘 I/O 次数）”。**

### 2. 操作系统与 InnoDB 的“页（Page）”机制
计算机不可能每次只从磁盘读 1 个字节，这样效率太低。
*   **操作系统**：一次性按 4KB 的**磁盘块（Block）**读取。
*   **InnoDB 存储引擎**：将数据划分为连续的块，称为 **页（Page）**，**默认大小为 16KB**。
*   **物理定律**：InnoDB 每次从磁盘加载数据到内存（Buffer Pool），或者从内存刷盘，**最小单位都是 16KB 的整页** [5]。

---

### 3. 数据结构演进：为什么其他数据结构全灭？

#### ❌ 方案 1：链表 / 数组
*   **问题**：无序链表查一条数据要全表扫描；有序数组插入一条数据要移动后面所有数据，磁盘 I/O 爆炸。

#### ❌ 方案 2：二叉搜索树（BST）/ 红黑树（AVL）
二叉树每个节点只有 2 个子节点。
*   假设数据库有 **1000 万行数据**。
*   树的高度大约是 $h = \log_2(10000000) \approx 24$ 层。
*   这意味着：找一条数据，需要从根节点沿着指针往下找 24 次。如果每个节点存放在不同的磁盘页里，就要做 **24 次磁盘 I/O**！在毫秒级延迟下，查一条数据需要几百毫秒，系统直接卡死。

#### ❌ 方案 3：B 树（B-Tree，多路平衡搜索树）
B 树引入了**“高扇出（Fan-out）”**概念，即一个节点可以有几百甚至上千个子节点，树的高度骤降到 3~4 层。
但 B 树有一个致命缺陷：**B 树的非叶子节点也会存放真实的整行数据（Data）**。

*   假设一行数据 1KB，一个 16KB 的 InnoDB 页（节点）只能存 $16KB / 1KB = 16$ 条数据（包含指针）。
*   **扇出极低**：一个节点只能指向 16 个子节点。
*   要存 1000 万数据，树的高度依然会达到 6~7 层（需要 6~7 次磁盘 I/O）。
*   **范围查询灾难**：做 `WHERE id BETWEEN 10 AND 100` 时，B 树必须在树的各个层级之间上下回溯遍历，无法顺序读取。

---

#### ✅ 终极方案：B+ 树（MySQL InnoDB 选择的物理结构）

B+ 树对 B 树做了两项关键改造：

1.  **非叶子节点（目录页）“只存索引列键值 + 下一层页号指针”，绝不存真实数据**。
    *   因为不存真实数据，一个 16KB 的页可以塞下上千个指针！树的扇出能力暴增。
2.  **所有真实整行数据，统一存放在最底层的“叶子节点（数据页）”**。
3.  **所有叶子节点之间，通过“双向链表”首尾相连**。

---

## 二、 数学证明：为什么 3 层 B+ 树能存 2000 万行数据？

我们来做一次严密的物理计算，看看 B+ 树是如何把磁盘 I/O 控制在 3 次以内的。

### 假设条件：
*   InnoDB 页大小 = **16KB** = 16,384 字节（Bytes）。
*   主键类型 = `BigInt`（占 **8 字节**）。
*   指针大小 = 在 InnoDB 内约为 **6 字节**。
*   单条目录项大小 = $8 + 6 = 14$ 字节。
*   真实数据行大小 = 假设每行记录占 **1KB**（包含各种字符串、数值等）。

---

### 计算推导：

1.  **非叶子节点（根节点 / 中间节点）能存多少指针？**
    *   扣除页头页尾元数据（约 1KB），剩余约 15KB（15,360 字节）用于存目录。
    *   一个页能存的目录指针数 = $15360 / 14 \approx \mathbf{1100}$ **个指针**（扇出 = 1100）。

2.  **叶子节点（最底层数据页）能存多少行真实数据？**
    *   一个 16KB 的页，按每行 1KB 计算，能存 $16KB / 1KB = \mathbf{16}$ **行记录**。

3.  **计算 3 层 B+ 树的总容量：**
    *   **第 1 层（根节点，1 个页）**：拥有 1,100 个指向第 2 层页的指针。
    *   **第 2 层（中间节点，1,100 个页）**：每个页又拥有 1,100 个指针，共有 $1100 \times 1100 = 1,210,000$ 个指向第 3 层叶子页的指针。
    *   **第 3 层（叶子节点，1,210,000 个数据页）**：每个数据页存 16 行数据。
    *   **总容量** = $1,210,000 \times 16 = \mathbf{19,360,000}$ **行数据（约 1936 万行）**！

### 物理结论：
**在一个拥有 2000 万条记录的大表中，MySQL 只需要建立一棵 3 层的 B+ 树。找到任意一条数据，仅需要 3 次磁盘 I/O（如果根节点常驻内存，实际上只需要 2 次磁盘 I/O）！**

## 三、 聚簇索引 vs. 二级索引 的物理差异

在 InnoDB 中，所有数据都是通过 B+ 树组织的，这种存储模式称为**索引组织表（Index-Organized Table）** [2]。

```text
               聚簇索引 (Clustered Index)               二级索引 (Secondary Index: idx_scene)
             [ 根节点: 页号 3, 主键范围 ]               [ 根节点: 页号 10, scene_id 范围 ]
                        /     \                                    /     \
                       /       \                                  /       \
         [ 叶子页 A ]              [ 叶子页 B ]           [ 叶子页 C ]          [ 叶子页 D ]
   +----------------------+  +----------------------+  +--------------------+ +--------------------+
   | ID: 1, Scene: 'A',.. |  | ID: 3, Scene: 'C',.. |  | Scene:'A' -> ID:1  | | Scene:'C' -> ID:3  |
   | ID: 2, Scene: 'B',.. |  | ID: 4, Scene: 'D',.. |  | Scene:'B' -> ID:2  | | Scene:'D' -> ID:4  |
   +----------------------+  +----------------------+  +--------------------+ +--------------------+
   (包含整行数据的全部列)     (包含整行数据的全部列)     (只包含 scene_id + 主键 ID)
```

### 1. 聚簇索引（Clustered Index）
*   **定义**：按照表的主键构造的 B+ 树。
*   **物理特点**：**叶子节点直接包含该行的所有字段数据**（包括 `trx_id` 事务 ID、`roll_ptr` 回滚指针以及所有自定义列） [2]。
*   **数量**：一张表**有且仅有一个**聚簇索引（默认主键；无主键选第一个 Unique 列；再没有 InnoDB 自动生成 6 字节隐藏列 `DB_ROW_ID`）。

---

### 2. 二级索引（Secondary Index / 辅助索引）
*   **定义**：为非主键列（如 `scene_id`）建立的索引。
*   **物理特点**：叶子节点**不存整行真实数据**，只保存 **“当前索引列的值” + “对应的主键 ID”** [2]。
*   **为什么二级索引不直接存物理磁盘地址（比如：页号+页内偏移量）？**
    *   *深度原因*：当数据表发生 `INSERT` 或 `DELETE` 时，可能导致数据页满而触发**页分裂（Page Split）**。一旦页分裂，数据的物理磁盘地址会立刻改变！
    *   如果二级索引存的是物理地址，每次页分裂，MySQL 就必须去更新**所有**二级索引里对应的地址指针，这个维护代价是不可承受的。
    *   存“主键 ID”实现了**逻辑解耦**：物理地址变了，只有聚簇索引自己调整，二级索引完全不需要动。

---

## 四、 “回表”与“覆盖索引”的物理轨迹演练

为了彻底明白什么是“回表”和“覆盖索引”，我们追踪两条不同的 SQL 在物理内存和磁盘上的执行轨迹。

假设表结构如下：
```sql
CREATE TABLE landsat_metadata (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,  -- 聚簇索引
  scene_id VARCHAR(50) NOT NULL,          -- 二级索引 idx_scene
  cloud_cover DOUBLE NOT NULL,            -- 无索引
  KEY idx_scene (scene_id)
);
```

---

### 场景 A：触发“回表”的查询

```sql
SELECT * FROM landsat_metadata WHERE scene_id = 'LC08_001';
```

#### 物理执行轨迹：
1.  **搜寻二级索引树**：
    *   加载 `idx_scene` B+ 树的根节点页到内存。
    *   二分查找，沿着指针定位到 `idx_scene` 的叶子节点页。
    *   在叶子节点找到 `scene_id = 'LC08_001'` 的项，读取出绑定的主键 **`id = 42`**。
2.  **触发回表（Lookup）**：
    *   根据主键 **`id = 42`**，**重新回到聚簇索引 B+ 树** [2]。
    *   加载聚簇索引树的根节点页到内存。
    *   沿指针定位到聚簇索引的叶子节点页。
    *   在该页中读取 `id = 42` 的**整行记录**（提取出 `cloud_cover` 等所有字段） [2]。
3.  **物理开销**：遍历了 **2 棵 B+ 树**，读取了约 4~6 个页，产生了额外的内存/磁盘寻址。

---

### 场景 B：触发“覆盖索引（Covering Index）”的查询

```sql
SELECT id, scene_id FROM landsat_metadata WHERE scene_id = 'LC08_001';
```

#### 物理执行轨迹：
1.  **搜寻二级索引树**：
    *   加载 `idx_scene` B+ 树的根节点页到内存。
    *   定位到 `idx_scene` 的叶子节点页。
    *   在叶子节点找到 `scene_id = 'LC08_001'` 的项。
2.  **获取数据并直接返回**：
    *   SQL 要求的字段只有 `id` 和 `scene_id`。
    *   而 `idx_scene` 的叶子节点**恰好已经包含了这两个字段**！
    *   **查找直接结束，不再去聚簇索引树回表！**
3.  **物理开销**：只遍历 **1 棵 B+ 树**，磁盘 I/O 减少一半。
4.  **EXPLAIN 表现**：`Extra` 列会显式标注 **`Using index`**（代表成功使用了覆盖索引，消灭了回表）。

### 实验 3：Linux 权限实操与二进制计算

在 Linux 系统管理中，每一个文件都有权限控制。

#### 1. 查看当前 `.ibd` 文件的权限：
```bash
ls -l landsat_metadata.ibd
```
输出：`-rw-r----- 1 mysql mysql 114688 ... landsat_metadata.ibd`

#### 2. 位运算与二进制转换：
Linux 权限由三组 `rwx` 组成（Owner、Group、Others）：
*   `r` (Read) = $2^2 = 4$ (二进制 `100`)
*   `w` (Write) = $2^1 = 2$ (二进制 `010`)
*   `x` (Execute) = $2^0 = 1$ (二进制 `001`)

当前的 `-rw-r-----` 对应：
*   所有者 (mysql)：`rw-` = $4 + 2 + 0 = 6$
*   所属组 (mysql)：`r--` = $4 + 0 + 0 = 4$
*   其他用户：`---` = $0 + 0 + 0 = 0$
*   **三位八进制数字即为 640**。

#### 3. 动手修改权限并验证：
在容器内运行以下命令，将文件权限修改为 `755`，并将所有者改为 `root`：

```bash
-- 修改权限为 755 (rwxr-xr-x)
chmod 755 landsat_metadata.ibd

-- 修改属主为 root
chown root:root landsat_metadata.ibd

-- 查看修改后的结果
ls -l landsat_metadata.ibd
```

**期望输出**：
`-rwxr-xr-x 1 root root 114688 ... landsat_metadata.ibd`

*物理安全含义*：如果将 `.ibd` 文件赋予 `755` 或 `777` 权限，系统上的任意普通用户都可以用 `cat` 或 `hexdump` 读取甚至篡改数据库的物理文件，造成严重的安全泄露！因此生产环境中，MySQL 数据目录必须严格限定为 `mysql:mysql` 属主与 `600` 或 `640` 权限。

## 参考答案

### 1. 物理证明逻辑
在 InnoDB 里，`scene_id` 这类字段通常建立的是二级索引。二级索引的叶子节点里没有整行数据，而是只存了“索引列值 + 主键 ID”。所以当执行：

```sql
SELECT * FROM table WHERE scene_id = 'xxx';
```

MySQL 先在二级索引树上找到对应的 `scene_id`，拿到对应的主键 `id`，然后再回到聚簇索引（主键索引）树上去取整行数据，因此要遍历 2 棵 B+ 树。

而执行：

```sql
SELECT id FROM table WHERE scene_id = 'xxx';
```

时，二级索引叶子节点里已经包含了 `id`，所以只需要在二级索引树上把结果取出来就行，不需要再回表去查聚簇索引，因此只需要遍历 1 棵 B+ 树。

题目 1：聚簇索引 vs. 二级索引与“回表”物理证明
满分标准表达：
物理存储差异：InnoDB 存储引擎将聚簇索引的叶子节点设计为保存整行记录的所有列字段（包含 DB_TRX_ID 事务 ID 和 DB_ROLL_PTR 回滚指针） [2]；而二级索引的叶子节点仅包含“索引列的值”与“对应的主键 ID” [2]。
回表触发机制：当执行 SELECT * FROM ... WHERE scene_id = 'xxx' 时，优化器首先检索二级索引 B+ 树定位到匹配项，提取出主键 id；随后必须拿着该 id 重新检索聚簇索引 B+ 树以获取未保存在二级索引中的其他字段 [2]。这被称为“回表”，会引发额外的磁盘随机 I/O [2]。
覆盖索引消灭回表：当执行 SELECT id, scene_id ... WHERE scene_id = 'xxx' 时，所需列完全被二级索引叶子节点覆盖。优化器检测到这一物理事实后，跳过对聚簇索引的检索，直接返回二级索引中的数据，触发“覆盖索引（Covering Index）” [2]。EXPLAIN 的 Extra 列显式标注 Using index 正是这一物理优化路径的标志。
