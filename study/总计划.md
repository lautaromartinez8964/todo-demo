### ⚙️ 架构设计铁律：Go 管编排，Python 管计算

这是 GeoAgent 项目最重要的工程决策，也是面试时最能体现「架构思维」的点：

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│   Go (Gin) 的职责                Python (FastAPI) 的职责      │
│   ─────────────                  ──────────────────          │
│   · HTTP API 网关                · YOLO 目标检测推理(GPU)     │
│   · 用户认证与鉴权(JWT)          · GeoTIFF 元数据解析         │
│   · 业务逻辑编排                   (rasterio, pip install)    │
│   · 消息队列投递(RabbitMQ)       · 影像分块与预处理           │
│   · 缓存管理(Redis)              · 影像缩略图生成             │
│   · 数据库操作(PostgreSQL)       · 空间坐标转换(GDAL绑定)     │
│   · SSE 流式推送                 · 未来：变化检测/语义分割    │
│   · RAG 管道编排                                       │
│                                                              │
│   铁律：                       铁律：                         │
│   ❌ 绝不引入 CGO 依赖           ❌ 不处理 HTTP/消息队列       │
│   ❌ 不做图像像素级处理          ❌ 不直接操作业务数据库       │
│   ❌ 不装 GDAL/OpenCV           ✅ 只做「输入路径→返回JSON」   │
│                                                              │
│   通信：HTTP REST（JSON） — 简单、可调试、够用                 │
│   不引入 gRPC：GeoAgent 规模不需要，REST 运维成本更低          │
└──────────────────────────────────────────────────────────────┘
```

**为什么这样设计？** 因为 CGO（Go 调用 C 库）是跨语言开发的著名陷阱——`libgdal-dev` 的动态链接版本冲突会让你陷入数天的编译报错地狱。而 Python 的 `rasterio` / `GDAL` 生态一条 `pip install` 就搞定。Go 擅长的是高并发网络编排（goroutine + channel），不是图像处理。让每种语言做它最擅长的事。

**面试时可以这样说**：「这个项目体现了异构语言协作的工业界实践——Go 作为编排层负责高并发的网络服务和业务逻辑，Python 作为计算层负责 GPU 推理和空间数据解析。两者通过 HTTP REST 松耦合通信，各自独立部署和扩缩容。」

#### —— Week 3-4（6.29 ～ 7.12）：MySQL ——

```
必掌握清单：
  1. B+树索引结构
     — 为什么 B+树：矮胖（减少磁盘 IO）、叶子节点双向链表（范围查询快）
     — 为什么不用 B 树：B 树非叶子存数据，扫全表效率低
     — 为什么不用哈希：哈希不支持范围查询
     — 为什么不用跳表：跳表层高随机，磁盘 IO 不可控
  2. 聚簇索引 vs 非聚簇索引
     — 聚簇索引：叶子节点存整行数据，一张表只有一个（通常是主键）
     — 非聚簇索引：叶子节点存主键 ID，查到后还要回表
     — 覆盖索引：查询列全在索引里，不需要回表（EXPLAIN Extra 显示 Using index）
  3. 事务与隔离级别
     — ACID 各字母的含义，InnoDB 怎么实现每个字母
     — 四种隔离级别：读未提交/读已提交/可重复读/串行化
     — 各自解决什么问题：脏读/不可重复读/幻读
     — InnoDB 默认「可重复读」，但通过 Next-Key Lock 也防住了幻读（面试陷阱题）
  4. MVCC 多版本并发控制
     — ReadView + undo log 版本链 → 快照读的原理
     — 事务 ID 的可见性判断规则
  5. 锁体系
     — 行锁（Record Lock）/ 间隙锁（Gap Lock）/ Next-Key Lock = 行锁 + 间隙锁
     — 什么时候加间隙锁：可重复读隔离级别下，防止幻读
     — 死锁：两个事务互相等待对方的锁，InnoDB 会自动检测并回滚一个
  6. EXPLAIN 实战（这比背书重要）
     — 在 todo-demo 项目里写 5 条不同复杂度的查询，单独跑 EXPLAIN
     — 看懂：type（ALL/index/range/ref/const）、rows、Extra（Using filesort/temporary）
     — 实战：给一条慢查询建索引，看 EXPLAIN 从 ALL 变成 ref

学习材料：
  主力：星球八股文 PDF MySQL 部分 → 建立面试框架
  深挖：《MySQL是怎样运行的》精读索引、事务、锁三章即可
  产出：5 条 GORM 查询 + EXPLAIN 分析，贴在笔记里

Linux 并行线：
  Week 3: chmod（数字法+符号法）/ chown / ps aux / top / kill
  Week 4: df -h / du -sh / lsof -i / netstat -tlnp / ss -tlnp

Git 并行线：
  Week 3: git stash / git stash pop / git cherry-pick
  Week 4: git rebase -i HEAD~3（交互式变基，squash/reword 实操）

#### —— Week 5-6（7.13 ～ 7.26）：Redis ——

```

  1. 五种数据结构底层实现（这是面试必考题）

     — List：3.2 前用压缩列表或双向链表；3.2 后用 QuickList（双向链表+压缩列表混合）
     — Hash：数据少用压缩列表，数据多用哈希表
     — Set：数据少用有序整数集合（IntSet），数据多用哈希表
     — ZSet：数据少用压缩列表，数据多用跳表（skiplist）+ 哈希表
  2. 持久化
     — RDB：全量快照，fork 子进程写，不影响主进程。「save」和「bgsave」的区别

#### —— Week 7（7.27 ～ 8.2）：网络 + 操作系统 ——

```
必掌握（聚焦面试最高频 7 个问题，不铺开）：

  1. TCP 三次握手/四次挥手
     — 三次握手为什么不是两次：防止旧连接请求到达服务端导致资源浪费
     — 四次挥手为什么是四次：TCP 是全双工的，双方都要关闭自己的发送方向
     — TIME_WAIT 为什么等 2MSL：确保最后的 ACK 被对方收到；让旧连接的数据包在网络中消失
     — SYN 洪泛攻击原理 + SYN Cookie 防御

  2. TCP 可靠传输
     — 滑动窗口：发送方窗口 = min(拥塞窗口, 接收方窗口)
     — 拥塞控制四阶段：慢启动 → 拥塞避免 → 快重传（3个重复ACK）→ 快恢复

  3. HTTP 版本演进
     — HTTP/1.1：持久连接（Keep-Alive）、管线化（队头阻塞问题）
     — HTTP/2：多路复用（单 TCP 连接多 Stream）、头部压缩（HPACK）、服务器推送
     — HTTP/3：QUIC 协议（基于 UDP），0-RTT 握手，彻底解决队头阻塞

  4. HTTPS
     — 握手过程：客户端随机数 + 服务端随机数 + Pre-Master Secret → 会话密钥
     — 非对称加密（RSA/ECDHE）交换对称密钥 → 对称加密（AES）传输数据
     — CA 证书链校验原理

  5. 进程 vs 线程 vs 协程
     — 进程：资源分配的最小单位，有独立内存空间
     — 线程：CPU 调度的最小单位，共享进程内存
     — 协程：用户态调度，切换不经过内核，成本极低（Go 的 goroutine 就是）

  6. IO 多路复用
     — select：fd_set 位图，有 1024 上限，每次调用需全量拷贝到内核
     — poll：pollfd 数组，无上限，但仍需全量拷贝
     — epoll：红黑树存所有 fd，就绪链表只存活跃 fd → O(1) 获取就绪事件。事件驱动！

  7. 零拷贝
     — 传统文件传输：磁盘→内核缓冲区→用户缓冲区→socket 缓冲区→网卡（4次拷贝）
     — sendfile：磁盘→内核缓冲区→socket 缓冲区→网卡（2次拷贝，不经过用户态）
     — Go 里 io.Copy 在 Linux 上底层调用的就是 sendfile

**Week 2：遥感影像上传（8.24 ～ 8.30）**
```
改造范围：文件上传模块

⚠️ 核心原则：Go ↔ Python 分工法则
  ┌──────────────────────────────────────────────────────────┐
  │  Go 负责：高并发网络编排、API 网关、消息路由、业务逻辑    │

  │  通信方式：HTTP REST（简单够用，不引入 gRPC 额外复杂度）  │
  │  铁律：Go 端绝不引入任何 CGO 依赖（GDAL/OpenCV 等）！    │
  └──────────────────────────────────────────────────────────┘

  为什么？godal 等 Go GDAL 绑定底层依赖 CGO，在 WSL2/Docker 中配置
  libgdal-dev 动态链接库会导致数天的编译报错地狱，与学 Go 本身毫无关系。

    - 存储原始文件到本地/OSS
    - 将文件路径通过 HTTP 发给 Python 元数据解析服务
    - 接收 Python 返回的 JSON 元数据，写入 PostgreSQL 的 images 表
    - 生成缩略图：调 Python 服务（Pillow/rasterio 生成，Go 端只转发请求）

  □ Python 端（YOLO 微服务）新增元数据解析接口：
    POST /metadata/parse
    请求：{"image_path": "/data/images/xxx.tif"}
    响应：{
      "width": 10240, "height": 8192,
      "srid": "EPSG:32650",       // 空间参考系
      "resolution": 0.5,           // 米/像素
      "bands": 4,                  // 波段数（R/G/B/NIR）

━━━━━━━━━━━━━━━━━━━━━━━━━━

## ⚠️ 执行中必须记住的四条

1. **GeoAgent 不需要完美**：Level 2 的 6 个遥感化周里，如果时间不够，优先保 MCP 遥感工具（Week 3-4）和 SSE 结构化推送（Week 5）。这两个是面试最有得聊的。

2. **6.824 卡壳超过 5 天就跳过**：Raft 的一个 race condition 可以折磨你一周。设置止损线——超过 5 天没进展，标记问题，先推进 GeoAgent，周末回头再看。分布式系统调试里「睡一觉就有思路」是常态。

3. **12 月起，你的身份从「学习者」变为「求职者」**：每天第一件事不是学新东西，是看有没有新面试邀请。面试当天的白天复习面试公司的面经，晚上复盘。学习新知识排在面试复盘之后。

4. **Harness 叙事不是空谈**：你可以用「Agent Harness」这个词来提升项目描述的格局，但面试官追问时你要能回到具体代码——trace_id 存在哪个表、MCP 工具注册了几行代码、Strategy 接口定义了什么方法。**80% 工程细节 + 20% 概念升华**，永远是面试的黄金比例。
