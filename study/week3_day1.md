## 🟦 第一步：先动手（约 20 分钟，别跳）

打开你的终端（WSL），执行下面两条命令：

```bash
# 1. 启动一个 Redis 容器（你 docker 已经很熟了）
docker run -d --name redis-day1 -p 6379:6379 redis:7.0

# 2. 进入 Redis 的命令行
docker exec -it redis-day1 redis-cli
```

看到 `127.0.0.1:6379>` 这个提示符，说明成功。接下来**一条一条敲**下面这些命令，每次敲完都看输出：

```text
# ① 存一个短字符串
SET short_key "hello"

# ② 问 Redis：这个值底层用啥编码存的？
OBJECT ENCODING short_key
#   ↑ 你应该看到：embstr

# ③ 存一个长字符串（数清楚，敲 45 个 a）
SET long_key "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"

# ④ 再看它的编码
OBJECT ENCODING long_key
#   ↑ 你应该看到：raw

# ⑤ 存一个小哈希（2 个字段）
HSET user:101 name "tom" age "20"

# ⑥ 看它的编码
OBJECT ENCODING user:101
#   ↑ 你应该看到：listpack（老版本是 ziplist）
```

### 📋 记下你看到了什么

| 命令 | 输出 | 含义（先别管细节） |
|------|------|-------------------|
| `OBJECT ENCODING short_key` | `embstr` | 短字符串一种存法 |
| `OBJECT ENCODING long_key` | `raw` | 长字符串另一种存法 |
| `OBJECT ENCODING user:101` | `listpack` | 小哈希一种紧凑存法 |

**关键发现**：同样是一个字符串，短的和长的，Redis 底层用了**不同的存法**。这就是今天要弄懂的核心——**底层编码**。

> 💡 先记住一个画面：`OBJECT ENCODING` 就像「拆开快递盒看里面东西是怎么包装的」。这个命令是你整个 Redis 学习生涯最好的朋友。

## 🟨 第二步：Redis 到底是什么？（用你的专业类比）

**一句话**：Redis 是一个**放在内存里的超大字典**（Key-Value 数据库）。

用你的遥感专业对比一下就懂了：

| | PostgreSQL / PostGIS | Redis |
|---|---|---|
| 数据在哪 | 磁盘（NVMe SSD） | **内存（RAM）** |
| 读取速度 | 5～50 毫秒 | **< 1 毫秒（快 1000 倍）** |
| 适合 | 存全量数据、跑复杂空间 SQL | 存高频访问的缓存/计数器/锁 |
| 类比 | 存在硬盘里的**全量影像库** | 服务器内存里的**瓦片缓存** |

**Redis 在真实项目里的 3 大用途**（记住这三个，面试和项目都用得上）：

1. **缓存（Cache）**：把 MySQL 里读得特别频繁、但很少变的数据（比如遥感影像元数据、用户登录 Token）放 Redis。用户来了先查 Redis，查不到才去查磁盘数据库——把流量挡在磁盘外面。
2. **计数器（Counter）**：高并发下做「点赞数」「访问量」「接口限流」。Redis 的 `INCR` 是原子的，多线程同时加也不会错。
3. **分布式锁（Lock）**：多个 Go 服务同时跑，防止它们重复处理同一景遥感影像——谁先抢到锁谁处理。

> 🎯 这就是你 GeoAgent 项目里 Redis 的角色：会话缓存 + 进度存储 + （以后）分布式锁。

## 🟨 第三步：为什么 Redis 单线程却这么快？（面试第一必考题）

**问题**：别的数据库靠多线程扛并发，Redis 命令执行基本是单线程，凭什么 QPS 能到 10 万+？

答案就三根柱子，**一根一根来**：

### 柱子 1：纯内存访问
内存随机读写约 **100 纳秒**，SSD 磁盘约 **100 微秒**——差 **1000 倍**。地基在这，快是应该的。

### 柱子 2：单线程，无锁、无上下文切换
想象一家餐厅：

- **多线程** = 好几个服务员同时上菜，菜要抢、要协调（加锁），人多的时候光协调就累死。
- **单线程** = 只有一个服务员，按顺序一桌一桌上，**不用抢、不用锁**，反而又快又稳。

Redis 命令执行就是这个「唯一服务员」：命令一个一个按顺序执行，天然原子，**不需要给数据结构加任何锁**——这是单线程最大的礼物。

### 柱子 3：I/O 多路复用（epoll）——这是最关键的一根

这里有个大坑要绕开：**「单线程」不等于「一次只能服务一个客户」**。

- **传统阻塞 I/O**：1 个线程盯 1 个连接。1 万个连接 = 1 万个线程，内存直接爆。
- **epoll（I/O 多路复用）**：1 个线程**同时盯着 1 万个连接**，像监控中心的大屏——哪个窗口有人按铃（数据来了），就处理哪个，处理完继续盯。

所以 Redis 的真实模型是：**「1 个服务员 + 1 块监控大屏」**。连接再多也不怕，因为服务员不是挨个死等，而是「谁有需求处理谁」。

### 补充：Redis 6.0 的多线程是怎么回事？

面试官会追问：「那 6.0 不是引入多线程了吗？矛盾吗？」

不矛盾。6.0 的多线程**只用来做「端菜」**（网络 I/O：接收请求、打包响应），**「做菜」（执行命令）还是主厨一个人**。

```
客户端请求 → [多个传菜员 I/O线程] → 把命令递给 → [主厨 主线程 单线程执行]
客户端收到 ← [多个传菜员 I/O线程] ← 打包好响应 ←
```

**为什么这么拆？** 因为后来发现瓶颈变成了「端菜」（网卡读写+协议解析），那就多请几个传菜员；但「做菜」如果也变成多人，就得给菜谱（数据结构）加锁，得不偿失。所以**命令执行永远是单线程**。

## 🟩 第四步：String 底层——从 C 字符串到 SDS（重点）

现在回到你刚才敲的命令。为什么短字符串是 `embstr`，长字符串是 `raw`？要理解这个，得先知道 Redis 怎么存字符串。

### 4.1 老办法（C 语言字符串）有什么毛病？

C 语言里字符串就是个字符数组，**靠结尾的 `\0` 表示结束**。两个硬伤：

- **毛病 A：数长度很慢**。想知道字符串多长，得从头数到 `\0`，数完才知道，复杂度 $O(N)$。
- **毛病 B：存不了二进制数据**（对你的遥感场景是致命的）。遥感 TIF 的原始字节流中间如果有 `0x00`（就是 `\0`），C 语言会以为字符串结束了，**把后面的数据截断丢掉**——这叫「二进制不安全」。

> 遥感影像、图片、压缩包都是二进制数据，所以这个毛病必须解决。

### 4.2 解法：SDS（简单动态字符串）= 给字符串贴「长度标签」

Redis 的聪明办法：**在字符数组前面贴一张说明书（Header），上面写清楚这个字符串有多长**。

```
┌─────────┬───────────┬─────────────────────────────┐
│ 说明书    │           │                             │
│ len = 5 │  (数据区)  │  h  e  l  l  o               │
└─────────┴───────────┴─────────────────────────────┘
    ↑ 写着「这段数据有 5 个字节」
```

- **长度 O(1)**：不用数了，看一眼说明书就知道。
- **二进制安全**：不管数据中间有没有 `\0`，Redis 只看说明书上的 `len`，照 `len` 读。TIF、JPG 随便存。

### 4.3 再套一层「快递盒」：redisObject

Redis 里存的不只是字符串，还有 Hash、List 等好几种类型。为了统一管理，每个值外面都套一个标准**快递盒** `redisObject`，盒子上写：

- `type`：里面装的是 String 还是 Hash？
- `encoding`：里面东西是用哪种方式打包的？（`embstr` / `raw` / `listpack`…）
- `ptr`：指向真正数据的指针。

你现在知道 `OBJECT ENCODING` 查的是什么了——就是查**快递盒上「encoding」这一栏写的是啥**。

### 4.4 embstr vs raw：小件一个盒装，大件两个盒装

现在回答你刚才看到的：

- **`embstr`（短字符串 ≤ 44 字节）**：快递盒 + 数据 **粘在一起**，申请**1 次**内存，一整块连续。CPU 读起来快。
- **`raw`（长字符串 > 44 字节）**：快递盒一个内存块，数据另一个内存块，**用指针 `ptr` 连起来**，申请**2 次**内存。

```
embstr（≤44字节）：1块连续内存
┌─────────────────────────────┐
│ 快递盒(16B) │ 说明书(4B) │ 数据(≤44B) │   ← 全粘一起
└─────────────────────────────┘

raw（>44字节）：2块分开的内存
┌──────────┐   ptr指针   ┌───────────────────────────┐
│ 快递盒(16B)│ ─────────► │ 说明书 │ 数据(>44B)       │
└──────────┘             └───────────────────────────┘
```

### 4.5 为什么临界线刚好是 44 字节？（面试加分题，慢慢算）

Linux 内存分配器（jemalloc）最小按 **64 字节** 的格子发内存。

算一下 64 字节的格子能装多少数据：

```
64   （一个内存格子的总大小）
− 16  （快递盒 redisObject 占 16 字节）
− 4   （SDS 说明书 sdshdr8 占 3 字节 + 结尾 \0 占 1 字节）
─────
= 44  （剩下的空间，刚好装数据）
```

所以：**数据 ≤ 44 字节 → 一个格子塞得下 → embstr（1 次内存）**；**数据 > 44 字节 → 一个格子塞不下 → raw（2 次内存）**。

> 🎯 这就是你刚才敲的 45 个 `a` 变成 `raw` 的原因——45 > 44，一个格子装不下了。

## 🟩 第五步：Hash 和 List 底层（一句话版 + 一张图版）

刚才你敲了 `HSET user:101 name "tom" age "20"`，输出 `listpack`。意思是：

### Hash：小的时候紧凑，大了变字典

- **数据量小**（字段少、值短）→ 用 `listpack`（压缩列表）：**一整块连续内存**，把所有字段挨个排好，省内存（省掉了指针开销）。
- **数据量大** → 升级成 `hashtable`（字典）：真正带哈希的查找结构。

中间有个关键机制叫 **渐进式 Rehash**：从「压缩列表」升级到「哈希表」时，**不是一次性搬家卡死主线程**，而是每次操作顺便搬一点点，搬完为止——像搬家不是一天搬完，而是每天搬几箱。

### List：quicklist = 货车拉集装箱

- 老办法：`ziplist`（一块连续内存）或 `linkedlist`（双向链表）。
- **Redis 3.2+ 统一用 `quicklist`**：它是**双向链表 + 压缩列表的结合**——链表的每个节点，本身是一个小压缩列表（ziplist）。

```
quicklist = 一列货车（链表节点）
每个货车车厢里装着一摞货（一个小 ziplist）
```

为什么这样设计？纯链表每个元素都要 `malloc` 一次（内存碎片多）；纯 ziplist 一扩容就要整块大拷贝。**「链表套压缩列表」两头的好处都要**。

## ⚔️ Day 1 杀手题（用今天的话术就能答）

**问：「Redis 6.0 引入了多线程，执行 `INCR` 命令时为什么依然不需要加锁？」**

**四步回答**：

1. **结论**：6.0 的多线程只用于网络 I/O（接收请求、打包响应），**命令执行依然是主线程单线程**。
2. **分层**：多个「传菜员」I/O 线程负责端菜，主线程（主厨）一个人负责做菜——执行 `INCR`。
3. **原因**：命令单线程执行，天然原子、无锁、无死锁；如果命令也并行执行，就得给数据结构加锁，得不偿失。
4. **加分**：这种设计让网络吞吐量提升约 2 倍，同时完全没引入并发安全问题。
